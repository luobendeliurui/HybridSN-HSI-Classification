## 三、与原仓库要求的差异（以及为什么改）

原仓库 README 的要求：`pytorch 1.9.0` / `scikit-learn 1.0.2` / `spectral 0.22.2` / `torchinfo 1.6.1`
（任务允许使用更高版本，因此本环境整体"等于或高于"这些要求。）

| 依赖 | 原要求 | 本环境 | 差异原因 |
|---|---|---|---|
| **pytorch** | 1.9.0 | **2.10.0** | ① PyTorch 1.9.0 在 PyPI 上**只发布到 cp39** 的 wheel，本机 Python 为 3.10，没有可用安装包；② 1.9.0 自带 CUDA 为 10.2/11.1，**不支持 RTX 5060 的 sm_120 (Blackwell) 架构** —— 即使安装成功也无法调用 GPU。sm_120 需要 CUDA 12.8 及以上。 |
| **scikit-learn** | 1.0.2 | 1.7.2 | 满足"更高版本"，所使用 API（PCA / train_test_split / metrics）保持兼容 |
| **spectral** | 0.22.2 | **0.22.4** | 0.22.2 在 PyPI 上**仅发布源码包（tar.gz）**，Windows 下编译需要 MSVC 编译器（本机未安装任何 C 编译器）。0.22.3 / 0.22.4 提供**纯 Python wheel**（`py3-none-any`），且被 notebook 使用的 API 完全一致（imshow / save_rgb / spy_colors / view_cube），**代码无需修改**。 |
| **torchinfo** | 1.6.1 | 1.8.0 | 满足"更高版本"，对 PyTorch 2.x 兼容性更好 |

> **原作者环境（从 notebook 元数据解析）**：`Python 3.7.11`，conda 环境名 `pytorch-gpu`。
> 这解释了为何其锁定 `pytorch 1.9.0` —— 那是 2022 年前后 Python 3.7 可用且稳定的版本。
> 本机为 Python 3.10 + 新一代 GPU，故必须升版本。

## 五、主要训练参数（任务书必交项）

全部来自 `HybridSN.ipynb` 的配置单元与训练单元：

| 参数 | 值 |
|---|---|
| **Epoch** | **100** |
| **Batch Size** | **256** |
| **Learning Rate** | **0.001** |
| **Optimizer** | **Adam**（`weight_decay = 1e-6`） |
| **损失函数** | `CrossEntropyLoss` |
| 训练 / 验证 / 测试比例 | **30% / 10% / 60%** |
| 随机种子 | 666 |
| PCA 保留分量 | 15（`PCA(n_components=15, whiten=True)`，**含白化**） |
| Patch（空间窗口）尺寸 | 25×25 |
| Dropout 比例 | **0.4**（论文未报告该值，代码中为 `p=0.4`） |
| 验证 / 保存间隔 | 每 5 个 epoch 验证一次并保存 `epoch_{e}_acc_{val}.pth` |
| 设备 | `cuda:0`（代码含 CPU 回退逻辑） |

**网络结构**（与论文表 I 对应）：
`3×Conv3d(1→8,(7,3,3) / 8→16,(5,3,3) / 16→32,(3,3,3))` → `reshape` → `Conv2d(96→64,3×3)` → `Flatten` → `Linear(18496→256)` → `Dropout(0.4)` → `Linear(256→128)` → `Dropout(0.4)` → `Linear(128→9)`

**实测模型规模**（`torchinfo.summary()`）：

| 项目 | 值 |
|---|---|
| **Total params** | **4,844,793** |
| Trainable / Non-trainable | 4,844,793 / 0 |
| **Total mult-adds** | **50.95 M** |
| Params size | 19.38 MB |

> **为何不是论文表 I 的 5,122,176？**
> 论文表 I 对应 **IP 数据集**（PCA 30 维、16 类），本实验为 **PU**（PCA 15 维、9 类），
> 因此 conv2d 输入通道为 32×3 = **96**（而非 32×18 = 576）、输出层为 **9** 类（而非 16）。
> 逐层参数与形状链已全部核对一致：`[1,15,25,25] → [1,8,9,23,23] → [1,16,5,21,21] → [1,32,3,19,19] → [1,96,19,19] → [1,64,17,17] → [1,18496] → [1,256] → [1,128] → [1,9]`

## 六、如何运行（复现步骤）

### 1. 安装依赖（一条命令）

```bash
cd HybridSN-HSI-Classification
pip install -r requirements.txt
```

> `requirements.txt` 中已通过 `--extra-index-url https://download.pytorch.org/whl/cu130`
> 声明 PyTorch 官方索引，因此**一条命令即可完成完整安装**，无需分两步。

**若 pip 报 `ProxyError` / `SSLError`**（本机实测遇到），显式指定代理：

```bash
pip install -r requirements.txt --proxy http://127.0.0.1:7897
```

### 2. 环境自检

```bash
python check_env.py
```

逐项核对 Python / PyTorch / CUDA / GPU / 数据集可读性，预期输出 `RESULT: ALL CHECKS PASSED`。

### 3. 运行实验

**方式 A（本次实际采用）：在 VS Code 中运行原始 notebook**

```bash
cd HybridSN-HSI-Classification
code .
```

1. 打开 `HybridSN.ipynb`
2. 右上角 **Select Kernel** → 选择 **Python 3.10.0**（路径含 `pyenv-win\versions\3.10.0`）
3. 将第 **2** 个代码单元的 `DATASET = 'SA'` 改为 **`'PU'`**
4. 菜单选择 **Restart Kernel → Clear All Outputs**，然后从第 1 格开始，用 `Shift+Enter` **逐格运行**
   （⚠️ 必须从第 1 格开始：内核重启后内存为空，跳格运行会报 `NameError`）
5. 运行至第 **17** 格（训练循环）后等待约 **5–6 分钟**

**方式 B（备用）：命令行运行等价脚本**

```bash

```

> ② `from tqdm.notebook import tqdm` → `from tqdm import tqdm`。**其余代码完全一致。**
> 使用该脚本同样需先将其配置区的 `DATASET = 'SA'` 改为 `'PU'`。

**方式 C（备用）：JupyterLab**

> 注意需使用 `python -m jupyter`（本机 `Scripts` 目录未加入 PATH，直接敲 `jupyter` 会提示找不到命令）。

### 7.4 差异分析

本次复现 OA 为 0.99949，与作者报告值 0.99973 相差 **0.024 个百分点（约 6/25,667 个测试像素）**，差异来源：

| 来源 | 说明 |
|---|---|
| **cuDNN 非确定性算子** | 部分卷积 / 规约算法在 GPU 上并行执行时浮点累加顺序不固定，每次结果略有不同 |
| **库版本差异** | 作者为 PyTorch 1.9.0 + Python 3.7.11；本环境为 PyTorch 2.10.0 + Python 3.10.0 |
| **硬件架构差异** | 不同 GPU 架构（sm_120 vs 作者当年的显卡）底层算子实现不同 |
| **随机种子仅能固定部分环节** | 代码固定了 `RANDOM_SEED = 666`，但 cuDNN 算法选择仍可能受硬件影响 |

**结论**：差异处于随机波动范围内，**判定为成功复现**。

## 八、复现过程中遇到的问题与解决

| # | 问题现象 | 排查过程 | 原因 | 解决方式 |
|---|---|---|---|---|
| 1 | `pip install jupyterlab` 报 `ProxyError: Cannot connect to proxy`，重试后 `SSLError: EOF occurred in violation of protocol` | 用 `Invoke-WebRequest` 测试索引页可正常返回 200，说明网络本身通；再检查 `urllib.request.getproxies()` 返回 `{}` | 本机 DNS 为 Clash 的 **fake-ip 模式**（解析结果指向 `198.18.0.x`），**必须经代理访问**；但系统代理开关关闭，pip 探测不到代理，于是直连假 IP 而失败 | 显式指定代理：`pip install ... --proxy http://127.0.0.1:7897` |
| 2 | `spectral==0.22.2` 无法安装 | 查 PyPI 发现该版本仅有 `tar.gz` 源码包 | 0.22.2 是该系列唯一只发源码包的版本，Windows 下编译需要 MSVC（本机无 C 编译器） | 改用 **0.22.4**（提供纯 Python wheel），所用 API 完全一致，代码无需修改 |
| 3 | 无法安装 `pytorch==1.9.0` | 查 PyPI 版本列表，最高只到 cp39；再核对 GPU 计算能力为 `(12,0)` = sm_120 | ① 无 Python 3.10 对应 wheel；② 1.9.0 自带 CUDA 10.2/11.1 不支持 sm_120 | 升级至 **torch 2.10.0+cu130**（CUDA 13.0 ≥ 12.8，支持 sm_120） |
| 4 | `jupyter lab` 提示"无法将 jupyter 项识别为 cmdlet…" | `pip list` 显示 JupyterLab 4.6.3 已安装；检查 PATH 发现只有 `pyenv-win\bin` 与 `shims`，**缺少 `versions\3.10.0\Scripts`** | pyenv-win 未将当前 Python 版本的 `Scripts` 目录加入 PATH，故包自带的命令行工具找不到 | 改用 **`python -m jupyter lab`**（绕过 PATH，通用解法） |
| 5 | 第 12 格输出的样本统计表是 **16 类、合计 54,129** | 对照 PU 已知统计（9 类、42,776），发现不符；查文件确认 `DATASET` 已是 `'PU'`，但该格**执行计数仍为 183**（自己的格子是 4~15） | **两个原因叠加**：① 改 `DATASET` 后未重新运行依赖它的单元格；② 更主要的是**屏幕上显示的是作者保存在 `.ipynb` 中的历史输出**，并非本次运行结果 | 用 **Restart Kernel + Clear All Outputs** 清空全部旧输出后从第 1 格重跑，并养成**用单元格左侧执行计数判断输出新旧**的习惯 |
| 6 | 执行第 17 格报 `NameError: name 'torch' is not defined`（`Cell In[1]`） | 报错显示 `In[1]`，说明这是重启内核后执行的第 1 格 | 重启内核后内存为空，直接跳到中间格运行，前面 16 格从未执行，`torch` 等名字不存在 | 必须**从第 1 格开始按顺序运行**；内核重启后不可跳格 |
| 7 | 执行 `spectral.imshow()` 出现 `UserWarning: Failed to create RectangleSelector object` | 检查确认该格输出正常（图像已显示、`save_rgb` 已写出文件），执行计数已更新 | `RectangleSelector` 是 matplotlib 的**交互控件**，而 Jupyter 的 `%matplotlib inline` 为**静态渲染**，不支持交互控件 | **属无害警告**，不影响图像显示与保存，无需处理 |

> **小结**：其中第 1、2、3、4 项属于环境配置类问题，第 5、6 项属于 **Jupyter 有状态执行**的典型陷阱
> （"改了代码不等于改了内存中的变量""重启内核后必须从头运行""屏幕上的输出可能是历史输出"），
> 第 7 项为无害警告。
